## 3. 性能测试

### 3.1 测试类说明

| 类 | `demo.PerformanceTest` |
|----|------------------------|
| 运行 | `mvn compile exec:java@perf` |
| 可选参数 | `吞吐条数 延迟采样数 扇出消息数`（默认 `10000 1000 100`） |
| 快速试跑 | `mvn compile exec:java@perf -Dexec.args="2000 500 50"` |

### 3.2 测试项

| 序号 | 名称 | 方法 | 指标 |
|------|------|------|------|
| 1 | 多订阅者扇出 | 3 个 `SubscriberClient` 同订 `perf.fanout`，发布 M 条 | 每个订阅者收到 M 条 |
| 2 | 端到端延迟 | payload 含 `sendTime`，采样 N 次 | 平均延迟、P95、最小/最大（ms） |
| 3 | 端到端吞吐 | 1 发布者连续 N 条，1 订阅者计数 | 发布耗时、端到端条/秒、是否丢消息 |

延迟计算：`收到时刻 - payload.sendTime`（毫秒）。

吞吐计算：`N / (从首条发布到收齐 N 条的墙钟时间)`。

### 3.3 实测数据（示例）

> 在本地 Windows + JDK 22、Broker 单进程下执行  
> `mvn compile exec:java@perf -Dexec.args="10000 1000 100"`  
> 实际数值以你本机控制台输出为准，答辩前请在本机重跑并替换下表。

| 指标 | 结果（示例，待本机更新） |
|------|--------------------------|
| 扇出 100 条 × 3 订阅者 | 各 100/100，**通过** |
| 延迟采样 1000 | 平均约 **1~5 ms**（本机回环），P95 约 **5~15 ms** |
| 吞吐 10000 条端到端 | 约 **3000~8000 条/秒**（视 CPU、JDK、是否杀毒占用而定） |
| 丢消息 | 无（`CountDownLatch` 收齐） |

**示例控制台片段：**

```text
--- 1. 多订阅者扇出（并发投递）---
  订阅者 perf-sub-0 收到 100 / 100 条
  ...
--- 2. 端到端延迟 ---
  平均延迟: 2.35 ms
  P95 延迟: 8 ms
--- 3. 端到端吞吐 ---
  端到端吞吐: 5120 条/秒
  结果: 通过（无丢消息）
```

### 3.4 结果分析（可写入实验报告）

1. **扇出**：`SubscriptionRegistry` 按 topic 维护多 `ClientSession`，`MessageDispatcher` 对每条消息遍历订阅集合并 `PUSH`，故 3 个订阅者各收到一份副本，符合 Pub/Sub 语义。  
2. **延迟**：单机回环主要为 Socket IO + JSON 编解码 + 队列调度；未做持久化，延迟主要在毫秒级。  
3. **吞吐**：瓶颈通常在发布循环、单线程分发、同步写 Socket；可通过增大队列、批量写等优化（本实验未做）。  
4. **局限**：未测多发布者竞争、未测超大 payload、未测长时间稳定性。

## 4. 已知问题与说明

| 问题 | 说明 |
|------|------|
| `BindException: Address already in use` | 重复启动 Broker；先 `netstat -ano \| findstr :8888` 结束旧进程 |
| `mvn exec:java` 启动的是 Broker | 应使用 `exec:java@quicktest` / `@pssdemo` / `@perf` |
| 控制台中文乱码 | Windows 编码问题，不影响测试逻辑；可 `chcp 65001` |
