# 单机版消息中间件 — 项目分工与实现计划

> 面向 2 人结对编程，仅覆盖实验最低功能要求，不做过度设计。  
> 建议技术栈：**Java 17 + Maven + 原生 Socket**（实验允许 Netty 基础组件，但 Socket 更简单、依赖更少）。

---

## 1. 实验目标对照（做到即可）

| 要求 | 本项目的落点 |
|------|-------------|
| 事件驱动架构（EDA） | Broker 用「入队 → 事件循环线程消费 → 推送给订阅者」，业务系统只发/收事件，不直接互调 |
| 发布/订阅模式 | 代码中显式出现 `Publisher`、`Subscriber`、`Topic`、`Broker` 等角色 |
| 手写核心逻辑 | 注册、发布、订阅、路由全部自研，禁止引入 RabbitMQ/Kafka 等 |
| 单机多线程通信 | 一个 Broker 进程 + 多个 Client 线程/进程连接同一端口 |
| 场景演示 | 附一个「网络服务管理系统」Demo（见第 6 节） |
| 性能分析 | 用简单压测脚本统计吞吐、延迟（文档记录即可，不必做复杂监控平台） |

## 2. 技术栈（最小集）

| 层次 | 选型 | 说明 |
|------|------|------|
| 语言 | Java 17 | 与实验示例一致，便于序列化、并发库 |
| 构建 | Maven 单模块或多模块 | 推荐 3 个子模块：`broker-server`、`broker-client`、`demo-app` |
| 网络 | `java.net.ServerSocket` / `Socket` | 长连接；每条连接一个读线程或统一线程池 |
| 并发 | `ExecutorService`、`ConcurrentHashMap`、`LinkedBlockingQueue` | 实验明确要求 |
| 序列化 | JSON（推荐 `Jackson` 或手写简单 JSON） | 比 Java 原生序列化更易调试；跨语言为可选加分 |
| 日志 | `slf4j` + `logback` 或 `java.util.logging` | 便于结对调试 |
| 测试 | JUnit 5 | 单元测试 + 简单集成测试 |

**不引入**：Spring、RabbitMQ、Kafka、RocketMQ、Redis 等。

## 4. 核心设计（满足要点即可）

### 4.1 发布/订阅角色（模式必须可见）

```
Publisher  --publish(topic, msg)-->  Broker  --dispatch-->  Subscriber(s)
                ^                      |
                |                      +-- SubscriptionRegistry
                +---------- 仅通过 Broker 通信，彼此无直接引用
```

- **Broker**：被观察者 / 事件总线（维护主题与订阅关系，负责分发）。
- **Publisher / Subscriber**：观察者侧（通过 Client SDK 与 Broker 交互）。
- 业务 Demo 中的「告警服务」「监控大屏」等类，应**依赖 `BrokerClient` 接口**，而不是互相 `new` 对方。

### 4.2 服务端线程模型（简化版）

| 组件 | 职责 |
|------|------|
| `Accept` 线程 | `ServerSocket.accept()`，将新连接交给线程池 |
| 连接读线程（或池内任务） | 循环读帧 → 解析 `Command` → 更新注册表 / 消息入队 |
| `MessageDispatcher` 单线程 | `while(true) { msg = queue.take(); route(msg); }` |
| `HeartbeatMonitor` 定时任务 | 扫描 `lastHeartbeat`，关闭超时 `ClientSession` 并清理订阅 |

**线程安全**：

- `SubscriptionRegistry`：`ConcurrentHashMap<String, Set<ClientSession>>`（或 `CopyOnWriteArraySet`）。
- 待分发队列：`LinkedBlockingQueue<Message>`。
- 向某 Session 写 socket 时，对该 Session 的写操作加锁或使用单线程写队列，避免并发写乱序。

### 4.3 消息与协议（最小命令集）

**Message 字段**（客户端、服务端共用）：

| 字段 | 类型 | 说明 |
|------|------|------|
| topic | String | 主题，如 `network.alert` |
| payload | String | JSON 或纯文本业务内容 |
| timestamp | long | `System.currentTimeMillis()` |

**Command 类型**（一帧一条 JSON 或「长度 + JSON」）：

| 命令 | 方向 | 作用 |
|------|------|------|
| REGISTER | C→S | 客户端标识（clientId） |
| SUBSCRIBE | C→S | 订阅 topic |
| UNSUBSCRIBE | C→S | 取消订阅（可选，有时间再做） |
| PUBLISH | C→S | 发布消息，进入 `BlockingQueue` |
| PUSH | S→C | 服务端推送给订阅者 |
| HEARTBEAT | 双向 | 保活 |
| ACK | 双向 | 可选，收到 PUSH 后回 ACK（简单场景可省略） |

**粘包处理（二选一，选简单的）**：

1. 每行一个 JSON（`\n` 分隔）— 实现最快；或  
2. 4 字节长度 + body — 稍规范。

### 4.4 客户端要点

| 要点 | 实现 |
|------|------|
| 长连接 | `Socket` 连接 Broker 后不关闭 |
| `onEvent` | 实现 `MessageListener`，读线程收到 `PUSH` 后回调 |
| 重连 | 断线后 sleep + 重新 `connect` 并重新 `SUBSCRIBE`（可选增强，时间紧可只做日志提示） |

### 4.5 心跳（最低实现）

- 客户端每 30s 发 `HEARTBEAT`。
- 服务端记录 `lastHeartbeat`；超过 90s 无心跳则关闭连接，并从 `SubscriptionRegistry` 移除该 Session。

## 5. 两人分工（建议）

### 成员 A — Broker 服务端（约 50%）

| 序号 | 任务 | 产出 |
|------|------|------|
| A1 | 定义 `Message`、`Command`、编解码 | `protocol` 包 + `docs/协议说明.md` |

| A3 | `SubscriptionRegistry` 注册/订阅/退订 | 单元测试：同 topic 多订阅者 |
| A4 | `LinkedBlockingQueue` + `MessageDispatcher` 分发 | 发布一条消息，订阅者能收到 |

| A6 | 与服务端相关的集成测试、性能压测入口 | `docs/测试与性能报告.md` 服务端部分 |

### 协作节奏（结对编程）

| 阶段 | 两人一起完成 | 大致时间 |
|------|--------------|----------|
| 第 0 天 | 敲定协议 JSON 样例、端口（如 9090）、topic 命名 | 2h |

## 6. 场景演示：网络服务管理系统（最小剧本）

用中间件解耦三类角色（各开一个线程或进程，共连一个 Broker）：

| 角色 | 类型 | Topic | 行为 |
|------|------|-------|------|
| 探针/Agent | Publisher | `network.alert` | 定时或随机模拟「链路中断」「高延迟」事件 |
| 监控台 | Subscriber | `network.alert` | `onEvent` 打印告警，更新「当前告警列表」 |
| 工单服务 | Subscriber | `network.alert` | 收到告警后发布 `ticket.created` |
| 通知中心 | Subscriber | `ticket.created` | 打印「已通知运维」 |

**演示脚本（答辩 3 分钟）**：

1. 启动 `BrokerMain`。  
2. 启动 Demo：先订阅端，再发布端。  
3. 展示控制台：告警 → 工单 → 通知 两条链路均通过 Broker，类之间无直接调用。  

**解耦说明（写进架构文档）**：  
若去掉 Broker，监控台需直接依赖探针代码；引入 topic 后，探针只关心 `publish`，监控台只关心 `subscribe`，符合实验「生产者与消费者完全解耦」。

## 7. 非功能指标（简单可做）

在 `docs/测试与性能报告.md` 中记录即可：

| 指标 | 做法 |
|------|------|
| 吞吐 | 单 Publisher 连续发 N 条（如 10000），统计总耗时，条/秒 |
| 延迟 | 在 payload 中带 `sendTime`，Subscriber 收到后算 `now - sendTime`，取平均/ P95 |
| 并发 | 3 个 Subscriber 同 topic，验证每条消息都被收到 |

无需 Grafana、JMeter 复杂场景；写一个 `PerformanceTest` main 类输出数字足够。

## 9. 验收自检表（提交前勾选）

- [ ] 未使用 RabbitMQ / Kafka / RocketMQ 等现成中间件  
- [ ] 注册、发布、订阅、路由均为手写  
- [ ] 代码中能指出 Publisher、Subscriber、Broker、Topic  
- [ ] 单机多线程/多客户端可同时连接并通信  
- [ ] 使用 `BlockingQueue` 做异步缓冲 + 独立线程消费分发  
- [ ] 订阅关系使用 `ConcurrentHashMap`（或等价线程安全结构）  
- [ ] `Message` 含 topic、payload、timestamp  
- [ ] 客户端有 `onEvent` 回调  
- [ ] 心跳与失效连接清理  
- [ ] Demo 体现业务解耦  
- [ ] 有吞吐或延迟的简单测试数据

## 10. 有意不做的内容（避免过分设计）

以下**不在最低标准内**，时间充裕再考虑：

- 集群、主从、持久化磁盘队列  
- 消息 ACK 重投、死信队列、延迟队列  
- 鉴权、TLS、多租户  
- 管理 Web 控制台  
- 复杂流控、优先级队列  
- 跨语言客户端（保留 JSON 协议即可，不强制实现第二种语言）

## 11. 快速启动（实现完成后 README 可照抄）

```bash
# 1. 编译
mvn clean package -DskipTests

# 2. 启动 Broker（成员 A）
java -jar broker-server/target/broker-server.jar
# 或: mvn -pl broker-server exec:java -Dexec.mainClass=...BrokerMain

# 3. 启动 Demo（成员 B）
mvn -pl demo-app exec:java -Dexec.mainClass=...NetworkServiceManagementDemo
```

默认端口：`9090`。  
Demo 与 Client 通过系统属性或环境变量配置：`broker.host=127.0.0.1`、`broker.port=9090`。

## 12. 附录：Maven 父 POM 模块骨架（可选）

实现时可由一人初始化仓库：

```xml
<modules>
    <module>broker-server</module>
    <module>broker-client</module>
    <module>demo-app</module>
</modules>
```

`broker-client` 依赖协议 DTO 时，可抽 `broker-common` 模块放 `Message`/`Command`，避免复制粘贴；**仅一个 DTO 模块，不算过度设计**。
